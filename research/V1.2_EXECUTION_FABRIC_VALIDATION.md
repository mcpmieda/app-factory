# V1.2 — Execution Fabric Validation

Data: 2026-08-21

## Objetivo

Implementar e validar os itens 3, 4 e 5 da evolução pós-V1.1 sem Codex:

- abstração de backend de execução;
- current-agent/ChatGPT-first lane;
- GitHub Actions/CI como executor remoto determinístico.

## Arquitetura

### Capability routing

`engine/execution_engine.py` separa ação de executor. A ação vira um conjunto de capacidades obrigatórias e somente backends que cobrem 100% dessas capacidades podem ser candidatos.

Backends padrão:

- `current_agent`;
- `github_ci`;
- `sandbox` (somente quando declarado disponível);
- `local_full` (somente quando declarado disponível).

A ordem prioriza o backend mais leve, sem mascarar falta de capacidade.

### GitHub CI adapter

`engine/ci_executor.py`:

- descobre somente scripts de `package.json` em uma allowlist de IDs conhecidos;
- constrói argv estruturado (`npm run lint`, etc.) sem transformar texto livre em comando;
- reconhece validadores Python conhecidos;
- executa com `shell=False`;
- não aceita texto de prompt como comando;
- não exige secrets por padrão;
- não sugere instalação npm permissiva quando `package.json` não possui lockfile;
- interrompe a sequência após a primeira falha para manter evidência clara.

### Fallback

`.factory/execution.json` guarda apenas metadados bounded de tentativas e fica ignorado pelo Git por padrão.

O fallback é escopado por tarefa autônoma (`task_key`) + ação + backend. Duas falhas consecutivas fazem a próxima rota rejeitar aquele backend para a mesma tarefa; falhas de uma tarefa antiga não penalizam uma tarefa nova. Um sucesso posterior encerra a janela de falhas anterior.

O limite de repair continua no Autonomy Engine. Execution Fabric escolhe **onde** a próxima tentativa ocorre.

## Testes

`tests/v1_2/` cobre, entre outros contratos:

1. current-agent vence quando possui todas as capacidades;
2. CI é escolhido para verificação determinística;
3. browser headless permanece em CI;
4. browser interativo exige `local_full`;
5. backend incapaz nunca é escolhido;
6. falhas repetidas de CI escalam para sandbox disponível;
7. falhas recentes continuam válidas mesmo se houve sucesso mais antigo;
8. sucesso mais recente restaura CI como candidato;
9. falhas de tarefa antiga não contaminam tarefa nova;
10. histórico de execução não persiste logs multilinha/brutos;
11. gate discovery ignora script não allowlisted/malicioso;
12. CI plan declara ausência de shell/prompt/secrets;
13. projeto npm sem lockfile não recebe `npm install` permissivo;
14. validador Python conhecido executa sem shell;
15. gate ID desconhecido é rejeitado;
16. `resume` integra rota `current_agent`;
17. verificação do Autonomy Engine integra rota `github_ci`;
18. backend local não é assumido implicitamente.

`scripts/validate_v1_2.py` repete os contratos críticos em sessão/projeto temporário independente.

## CI

Workflow dedicado: `Validate V1.2 Execution Fabric`.

Ele executa:

- validação estrutural da Factory;
- regressão V1.1;
- validator V1.2;
- smoke de `route implement` e `route verify`;
- descoberta de gates do repositório.

Os workflows amplos da linha V1 permanecem obrigatórios antes do merge: plugin/bootstrap isolado, starter/recipes, PostgreSQL/Auth, audit project e browser E2E.

## Resultado

A V1.2 formaliza o padrão usado para construir a própria V1.1: o agente atual pode editar/revisar via GitHub, GitHub Actions executa prova reproduzível e um executor local completo só é necessário quando existe uma capacidade local/interativa concreta que a rota anterior não possui.

Isso reduz dependência de Codex sem reduzir Definition of Done e sem transformar CI em shell remoto aberto a prompts. O hardening final também impede que falhas antigas contaminem tarefas novas e exige lockfile para propor instalação reproduzível.
