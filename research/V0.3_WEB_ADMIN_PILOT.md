# V0.3 — Piloto web-admin

Data da execução: 2026-08-21

Issue: [#4 — Construir piloto web-admin pela App Factory](https://github.com/mcpmieda/app-factory/issues/4)

Revisão: [draft PR #6](https://github.com/mcpmieda/app-factory/pull/6)

Branch: `pilot/web-admin-v0.3`

## Resultado

O piloto entrega uma fatia vertical administrativa reproduzível em `pilots/web-admin/`: login/logout, área protegida, dashboard, Data Grid real do ReUI, busca, filtros, criação, edição, desativação reversível, exclusão permanente apenas de inativos, validação Zod, persistência SQLite e estados de loading/empty/error/success.

O fluxo foi verificado em Chromium desktop e viewport Pixel 7, inclusive persistência após reload e ausência de erros de console. O piloto permanece isolado; nenhum resultado experimental foi promovido ao Core.

## Aplicação da App Factory

- escala: **M — aplicação relevante**;
- Skills usadas na ordem do trabalho: `app-planner`, `architecture`, `ui-builder`, `database`, `security-review` e `verification`;
- roteamento: Codex, coerente com scaffold, terminal, migrations, autenticação, testes e browser;
- Spec Kit: **não instalado**. A Issue já fornecia domínio, stack candidata, critérios de aceitação, Definition of Done e handoff. Criar uma segunda camada de especificação teria duplicado artefatos sem reduzir incerteza. Foram usados como artefatos leves a própria Issue, este relatório, README, schema/migrations e testes executáveis;
- decisões evitadas: React Hook Form (um formulário pequeno é atendido por `FormData` + Server Actions), TanStack Query, Zustand, HeroUI, analytics, Sentry, Storybook e serviços externos.

## Arquitetura validada

```text
Browser
  ├─ Better Auth client ──> /api/auth/[...all] ──> Better Auth + Drizzle
  └─ React Server Components / Server Actions ──> Zod ──> repository ──> SQLite
```

- Next.js App Router e Server Components fazem leitura e composição do dashboard;
- Server Actions executam create/update/deactivate/reactivate/delete e revalidam a sessão em cada mutação;
- Better Auth usa adapter Drizzle; cadastro HTTP público fica desativado e um factory controlado habilita signup somente no seed local;
- Drizzle mantém schema único para autenticação e recursos, com duas migrations reproduzíveis;
- SQLite é criado dentro de `data/`, com WAL e foreign keys habilitadas;
- o registro guarda nome, categoria, status, localização, observações, atividade e timestamps;
- exclusão permanente exige que o registro já esteja inativo e confirmação explícita na UI.

## Problemas encontrados e correções

1. Better Auth 1.7 rejeitou `better-sqlite3@13` pelo peer `^12`; o piloto fixou 12.11.1.
2. O schema manual inicial não continha `account.issuer`; a CLI oficial gerou a referência e o schema foi alinhado.
3. A migration incremental gerada selecionava uma coluna `issuer` inexistente; a transformação segura usa o antigo `provider_id` para registros legados.
4. O registry ReUI instalou DnD, virtualização e Base UI não usados; arquivos e dependências foram removidos.
5. O ReUI gerado atualizava refs durante render, reprovado pelas regras atuais do React; o provider foi simplificado para contexto/memo compatíveis.
6. Better Auth recusou origem `127.0.0.1`; `localhost` e `127.0.0.1` foram explicitamente confiados apenas para o piloto local.
7. Acesso dinâmico ao filesystem fazia o Turbopack rastrear o projeto inteiro; o banco foi confinado estaticamente a `data/` e somente o basename configurável é aceito.

## Segurança

- nenhum segredo ou banco local está versionado;
- `.env.example` contém apenas placeholders;
- o script de setup grava um secret aleatório em `.env.local` com modo restrito quando suportado;
- signup externo está desativado;
- toda Server Action autentica novamente no servidor;
- entrada é validada por Zod; IDs são gerados no servidor;
- sessão e tabelas de auth usam FKs/cascade definidos pelo schema oficial;
- exclusão definitiva é bloqueada para registros ativos;
- não há dados reais, serviços externos ou telemetria adicionada pelo piloto.

## Limitações e decisão de promoção

- promover agora como defaults do **perfil web-admin**: TypeScript, Next App Router, Tailwind, shadcn, Better Auth, Drizzle, Zod, Vitest, Playwright e ESLint Next;
- manter ReUI como componente opcional recomendado após auditoria de arquivos/dependências gerados;
- manter Biome como formatter opcional complementar, não substituto automático do ESLint Next;
- manter SQLite/better-sqlite3 como alternativa local e de teste;
- antes da V1, reavaliar o advisory do `drizzle-kit`, testar um provider de produção e estabilizar um recipe de schema Better Auth gerado diretamente na criação do projeto.
