# V0.2 — Achados auditados

Este arquivo tem precedência sobre a matriz preliminar quando um candidato já passou por inspeção mais profunda.

## A-001 — `openai/skills` não deve ser usado como fonte atual

**Status:** confirmado

O README atual do repositório informa explicitamente que ele está **deprecated** e direciona usuários para `openai/plugins` e para o guia atual de plugins do Codex.

### Decisão

- `openai/skills` → **DESCARTAR como fonte atual**; manter somente como referência histórica.
- `openai/plugins` → **ADOTAR como referência principal do adaptador Codex**.
- O padrão aberto Agent Skills continua relevante; a depreciação é do catálogo antigo da OpenAI, não do conceito de Skills.

## A-002 — A integração principal com Codex deve ser um plugin, não apenas Skills soltas

**Status:** direção arquitetural forte; validar no piloto antes de congelar V1

O repositório oficial `openai/plugins` organiza cada plugin em `plugins/<nome>/` com manifest `.codex-plugin/plugin.json` e superfícies opcionais como:

- `skills/`;
- agentes;
- comandos;
- hooks;
- MCP;
- assets;
- configurações de app.

O plugin oficial `build-web-apps` demonstra exatamente esse modelo e contém Skills específicas para frontend, testes/debugging, React, shadcn, Stripe e Supabase.

### Decisão proposta

Manter dois níveis:

```text
APP FACTORY CORE
(portátil e neutro)
        │
        ├── Skills abertas
        ├── políticas
        ├── templates
        ├── testes/scripts
        └── estado/documentação

ADAPTADORES
        │
        ├── Codex Plugin
        ├── Claude adapter
        ├── Cursor adapter
        └── futuros agentes
```

O **Codex Plugin** deve ser a superfície preferencial da Factory no ecossistema OpenAI, sem tornar o núcleo dependente desse formato.

## A-003 — O plugin oficial `build-web-apps` é referência, não base para copiar integralmente

**Status:** confirmado por inspeção de Skill

A Skill `frontend-app-builder` do plugin oficial possui práticas fortes de design system, browser QA, implementação fiel, componentização e validação visual. Porém ela também é deliberadamente opinativa, incluindo um fluxo de geração visual e decisões de framework específicas.

### Adotar da ideia

- design como sistema, não coleção de estilos;
- browser verification antes de concluir;
- componentização e inventário de UI;
- coordenação entre Skills especializadas;
- usar ferramentas do projeto para descobrir contexto real;
- validar visual e comportamento, não apenas build.

### Não copiar como regra universal

- exigir Image Gen para toda UI nova;
- exigir aprovação visual humana em todo projeto;
- fixar React + Vite como default universal;
- impor heurísticas estéticas específicas a todos os produtos.

A nossa Factory precisa continuar adaptativa ao tipo de aplicação e ao objetivo do usuário.

## A-004 — A Skill oficial de shadcn reforça quatro regras da Factory

**Status:** confirmado

A Skill `shadcn-best-practices` do plugin oficial reforça:

1. **usar componentes existentes primeiro**;
2. **compor em vez de reinventar**;
3. consultar contexto real do projeto/CLI em vez de assumir configuração;
4. revisar arquivos adicionados por registries antes de considerar a instalação correta.

### Impacto

A Skill `ui-builder` da Factory deve evoluir na V0.3 para usar descoberta real via shadcn CLI/Registry/MCP quando o projeto tiver shadcn, em vez de depender apenas de conhecimento estático.
