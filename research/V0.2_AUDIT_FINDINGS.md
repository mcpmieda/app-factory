# V0.2 — Achados auditados

Este arquivo tem precedência sobre a matriz quando um candidato já passou por inspeção mais profunda.

## A-001 — `openai/skills` não deve ser usado como fonte atual

**Status:** confirmado

O repositório atual informa que foi depreciado e direciona para `openai/plugins` e para a documentação moderna de plugins.

### Decisão

- `openai/skills` → **DESCARTAR como fonte atual**; manter somente como referência histórica.
- `openai/plugins` → **ADOTAR como referência principal do adaptador Codex**.
- O padrão aberto Agent Skills continua relevante; a depreciação é do catálogo antigo da OpenAI, não do conceito de Skills.

## A-002 — A integração principal com Codex deve ser um plugin, não apenas Skills soltas

**Status:** confirmado em piloto real da Issue #3

A documentação atual do ecossistema OpenAI define plugin com manifest `.codex-plugin/plugin.json` e suporte a componentes como Skills, MCP servers, hooks e assets.

O piloto executado em 2026-08-21 confirmou que a própria raiz da App Factory pode ser instalada como plugin sem duplicar `skills/` ou `core/`. O Codex CLI oficial `0.149.0` reconheceu o marketplace local, instalou e habilitou `app-factory`, descobriu as 10 Skills e ativou quatro delas em smoke test. Os hashes origem/cache das Skills exercitadas foram idênticos e a CI passou com validação estrutural, Agent Skills e plugin.

### Decisão

Manter dois níveis:

```text
APP FACTORY CORE
(portátil e neutro)
        │
        ├── Skills abertas
        ├── políticas
        ├── templates
        ├── testes/scripts
        └── estado/documentação

ADAPTADORES
        │
        ├── Codex Plugin
        ├── Claude adapter
        ├── Cursor adapter
        └── futuros agentes
```

O **Codex Plugin** é a superfície preferencial da Factory no ecossistema OpenAI, sem tornar o núcleo dependente desse formato. A evidência completa está em `research/V0.2_CODEX_PLUGIN_PILOT.md`.

## A-003 — O plugin oficial `build-web-apps` é referência, não base para copiar integralmente

**Status:** confirmado por inspeção de Skill

O plugin oficial possui práticas fortes de design system, browser QA, componentização e validação visual, mas também inclui decisões deliberadamente opinativas.

### Adotar da ideia

- design como sistema, não coleção de estilos;
- browser verification antes de concluir;
- componentização e inventário de UI;
- coordenação entre Skills especializadas;
- usar ferramentas do projeto para descobrir contexto real;
- validar visual e comportamento, não apenas build.

### Não copiar como regra universal

- exigir geração de imagem para toda UI nova;
- exigir aprovação visual humana em todo projeto;
- fixar React + Vite como default universal;
- impor heurísticas estéticas específicas a todos os produtos.

## A-004 — A Skill oficial de shadcn reforça descoberta real e composição

**Status:** confirmado

A referência oficial reforça:

1. usar componentes existentes primeiro;
2. compor em vez de reinventar;
3. consultar contexto real do projeto/CLI em vez de assumir configuração;
4. revisar arquivos adicionados por registries antes de considerar a instalação correta.

### Impacto

A Skill `ui-builder` deve evoluir na V0.3 para usar descoberta real via shadcn CLI/Registry/MCP quando o projeto tiver shadcn.

## A-005 — Agent Skills deve ser tratado como padrão aberto real

**Status:** confirmado

A especificação atual define:

- `skills/<name>/SKILL.md` como unidade mínima;
- `name` obrigatório, até 64 caracteres, minúsculo, alfanumérico/hífen e igual ao diretório;
- `description` obrigatória, até 1024 caracteres e descrevendo o que a Skill faz e quando usar;
- campos opcionais como `license`, `compatibility`, `metadata` e `allowed-tools`;
- `scripts/`, `references/` e `assets/` como recursos opcionais;
- progressive disclosure como modelo de contexto;
- recomendação de manter `SKILL.md` abaixo de 500 linhas.

### Impacto

- manter Skills da Factory compatíveis com a especificação;
- validar automaticamente convenções essenciais;
- mover referências grandes para `references/` conforme as Skills crescerem;
- evitar formatos próprios quando o padrão aberto atender.

## A-006 — GitHub Spec Kit cobre boa parte da camada de planejamento

**Status:** forte candidato; integração deve ser proporcional à escala

O Spec Kit já formaliza o fluxo:

`constitution → specify → plan → tasks → implement`

com comandos opcionais para clarificação, análise, checklist, convergência e conversão de tarefas em Issues, além de suporte a muitos agentes.

### Decisão proposta

Não reconstruir um sistema spec-driven completo dentro da Factory.

- projetos XS/S → fluxo leve próprio;
- projetos M/L → avaliar adapter/preset compatível com Spec Kit;
- manter `core/PROJECT_SCALE.md` como roteador de profundidade;
- a Factory continua responsável por autonomia do usuário, roteamento de agentes, seleção de stack/UI, verificação e continuidade.

## A-007 — shadcn + ReUI está confirmado como eixo do perfil admin

**Status:** forte candidato a default do perfil `web-admin`

### shadcn

- licença permissiva;
- ativo;
- modelo copy-and-own;
- Registry e forte integração com agentes;
- permite composição sem lock-in de pacote visual fechado.

### ReUI

- licença MIT;
- ativo;
- copy-and-own;
- construído para ecossistema shadcn;
- biblioteca extensa de exemplos e componentes avançados como Data Grid, Event Calendar, Gantt, Kanban e Filters.

### Decisão

Manter `shadcn + ReUI` como combinação preferencial para o piloto admin.

## A-008 — HeroUI continua como perfil alternativo, não complemento obrigatório

**Status:** confirmado

HeroUI permanece ativo, TypeScript e Apache-2.0, com branch v3 e MCP oficial separado.

### Decisão

- usar HeroUI como **design system principal alternativo** quando o produto justificar;
- não misturar automaticamente com shadcn/ReUI;
- HeroUI MCP é integração útil quando esse perfil estiver ativo.

## A-009 — Better Auth + Drizzle têm integração concreta

**Status:** combinação forte para piloto, ainda não universal

Better Auth é framework-agnostic em TypeScript, cobre autenticação e autorização e possui adapter Drizzle próprio, documentação e geração de schema associada.

Drizzle é ativo, Apache-2.0 e suporta bancos comuns do ecossistema TypeScript.

### Decisão proposta

Testar `Better Auth + Drizzle` juntos no piloto `web-admin` antes de promovê-los a default. Auth e banco continuam módulos opcionais; projetos que não precisam deles não devem recebê-los.

## A-010 — Playwright é padrão forte de verificação; Playwright MCP é complementar

**Status:** confirmado

Playwright é ativo, Apache-2.0 e testa Chromium, Firefox e WebKit por uma API comum. Playwright MCP também é ativo e permite browser control por agentes.

### Decisão

- Playwright → forte candidato a padrão E2E em web apps relevantes;
- Playwright MCP → adapter de inspeção/interação para agentes;
- MCP não substitui suíte E2E versionada em CI quando o comportamento precisa ser repetível.

## A-011 — Starters externos devem inspirar composição, não virar nossa Factory

**Status:** confirmado

### `vercel/next-forge`

É um template de produção forte, mas traz várias integrações e decisões próprias. Serve melhor como referência arquitetural do que como clone universal.

### `Kiranism/next-shadcn-dashboard-starter`

É MIT, ativo, Next.js 16 + shadcn e explicitamente AI-friendly. Possui `AGENTS.md`, `CLAUDE.md`, Skills e organização feature-based, além de service layer para trocar backend.

### `create-t3-app`

É uma referência importante de **composição opcional de stack**, embora sua atividade de código seja menos recente que alguns candidatos atuais.

### `bulletproof-react`

Permanece uma referência útil de arquitetura React feature-based.

### Decisão

O starter da Factory deve ser componível e absorver padrões, não copiar um boilerplate inteiro com auth, billing, analytics e observabilidade impostos.

## A-012 — Zod, Vitest e Biome são candidatos fortes, mas com papéis diferentes

**Status:** parcial

- **Zod**: forte candidato padrão para contratos/validação TypeScript.
- **Vitest**: forte candidato para testes unitários/integração quando a stack for compatível.
- **Biome**: candidato de lint/format para simplificar tooling, mas deve ser testado contra requisitos reais de Next/React antes de substituir ESLint/Prettier universalmente.

## A-013 — O piloto Codex confirmou a estratégia de adaptador fino

**Status:** confirmado

A Issue #3 demonstrou que a Factory não precisa criar uma segunda distribuição para o Codex. O marketplace repo-local aponta para `./`, o manifest aponta para `./skills/` e o cache instalado reproduziu as Skills com hashes idênticos.

### Decisão

- manter uma única fonte de verdade para Skills;
- adaptar por manifest/configuração mínima;
- não adicionar MCP, hooks, apps ou assets sem caso concreto;
- manter o Core neutro;
- usar nova conversa/reinício quando o host exigir pickup de atualização do plugin.
