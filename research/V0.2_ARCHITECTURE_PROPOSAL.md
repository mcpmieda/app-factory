# V0.2 — Proposta de arquitetura após pesquisa

> Proposta em avaliação. Não é ainda a arquitetura congelada da V1.

## 1. Princípio

A App Factory não deve recriar ferramentas maduras que já resolvem bem uma camada do problema. Ela deve **orquestrar, selecionar e adaptar** essas ferramentas em torno do objetivo do usuário.

## 2. Arquitetura proposta

```text
USUÁRIO
  │
  ▼
APP FACTORY CORE
  ├── princípios
  ├── autonomia / menor trabalho humano
  ├── roteador ChatGPT ↔ Codex ↔ outros
  ├── classificação de risco
  ├── escala do projeto
  └── Definition of Done
  │
  ├──────────────► PLANNING LAYER
  │                 ├── fluxo leve próprio
  │                 └── Spec Kit adapter para projetos maiores
  │
  ├──────────────► BUILD LAYER
  │                 ├── Skills abertas
  │                 ├── starter selector
  │                 ├── UI selector
  │                 └── technology modules
  │
  ├──────────────► VERIFICATION LAYER
  │                 ├── lint / typecheck
  │                 ├── unit / integration
  │                 ├── Playwright
  │                 └── browser/MCP quando útil
  │
  └──────────────► AGENT ADAPTERS
                    ├── Codex Plugin
                    ├── Claude adapter
                    ├── Cursor adapter
                    └── outros
```

## 3. Core neutro

O Core continua em Markdown, Skills, scripts, Git e testes. Ele não depende de um fornecedor específico.

Responsabilidades do Core:

- entender o resultado real do usuário;
- minimizar trabalho manual;
- escolher ferramenta/agente;
- escolher profundidade do processo;
- definir critérios de conclusão;
- garantir continuidade pelo repositório;
- impedir complexidade sem retorno.

## 4. Planning Layer

### Projetos pequenos

Usar planejamento leve da própria Factory:

`objetivo → fluxos → decisões essenciais → blocos funcionais → execução`.

Não instalar CLI ou gerar muitos artefatos apenas por disciplina metodológica.

### Projetos médios/grandes

Avaliar **GitHub Spec Kit** como motor spec-driven.

O Spec Kit já oferece uma sequência madura:

`constitution → specify → plan → tasks → implement`

além de `clarify`, `analyze`, `checklist`, `converge` e conversão de tarefas para Issues.

A Factory pode atuar como preset/adapter ou consumir artefatos compatíveis em vez de duplicar todo esse sistema.

### Regra

Não tornar Spec Kit dependência obrigatória de todo projeto. A ativação depende de escala, risco e duração esperada.

## 5. Codex Adapter

A integração preferencial com o ecossistema OpenAI deve evoluir para um **Codex Plugin**.

Estrutura candidata:

```text
adapters/codex-plugin/
├── .codex-plugin/
│   └── plugin.json
├── skills/
├── hooks/
├── .mcp.json          # somente se necessário
└── assets/            # somente se necessário
```

O plugin empacota a superfície Codex, mas não vira a fonte principal das regras. Skills devem apontar para o Core ou ser geradas/sincronizadas a partir dele para evitar divergência.

### Hooks

Hooks só entram quando automatizarem proteção concreta. Não usar hooks apenas para adicionar cerimônia. Como plugins exigem revisão/confiança de hooks, cada hook deve ter justificativa clara.

## 6. Skills

Manter `skills/<nome>/SKILL.md` seguindo o padrão Agent Skills:

- `name` e `description` válidos;
- nome igual ao diretório;
- Skills curtas e focadas;
- `scripts/`, `references/` e `assets/` sob demanda;
- progressive disclosure;
- validação automática no CI.

## 7. UI Layer

### Perfil Admin

**shadcn + ReUI**.

- shadcn como plataforma copy-and-own e registry;
- ReUI para padrões avançados de sistemas/admin;
- TanStack Table quando necessário por componentes avançados.

### Perfil Visual

**HeroUI** como alternativa principal quando o produto pedir uma linguagem visual coerente com seu design system.

HeroUI MCP serve como referência/integração quando o agente precisar consultar a biblioteca.

### Acabamento

Magic UI pode ser módulo opcional para páginas e efeitos específicos, não base universal.

## 8. Stack web candidata para piloto

Ainda não é default definitivo:

- TypeScript;
- framework web escolhido conforme produto, com Next.js como forte candidato para apps full-stack;
- shadcn + ReUI no perfil admin;
- Better Auth quando autenticação própria TypeScript for adequada;
- Drizzle quando ORM/migrations tipadas fizerem sentido;
- Zod para validação de contratos;
- Vitest para unit/integration quando compatível;
- Playwright para E2E/browser;
- Biome como candidato a lint/format após teste de compatibilidade com a stack.

## 9. Starter architecture

Não clonar `next-forge` ou outro boilerplate integralmente.

O primeiro starter deve ser **componível**:

```text
base
  + ui-admin
  + auth?          opcional
  + database?      opcional
  + e2e            padrão para web app relevante
  + observability? opcional
  + payments?      opcional
  + monorepo?      opcional
```

Isso reduz dependências, segredos e integrações desnecessárias.

## 10. Verification Layer

Para web apps relevantes:

1. lint/format;
2. typecheck;
3. testes unit/integration relevantes;
4. build;
5. execução real;
6. Playwright/browser para fluxo crítico;
7. console e regressão direta;
8. diff/revisão proporcional ao risco.

Playwright MCP é um adaptador útil para permitir que agentes controlem o navegador, mas não substitui uma suíte E2E versionada quando o fluxo precisa ser repetível em CI.

## 11. Segurança

Padrão em camadas:

1. controles nativos da plataforma/repositório;
2. validação e testes do próprio app;
3. ferramentas adicionais apenas quando risco justificar — Gitleaks, OSV Scanner, Semgrep etc.

## 12. O que não entra como universal

- monorepo/Turborepo;
- Storybook;
- Sentry/OpenTelemetry;
- Renovate;
- release automation;
- pagamentos;
- banco;
- autenticação;
- MCP próprio;
- geração de imagem antes de toda UI;
- Spec Kit completo em tarefas pequenas.

Esses módulos são ativados por necessidade.

## 13. Próximo teste

Depois de concluir a auditoria P0/P1, criar dois pilotos:

1. **micro-piloto** — app pequeno para validar fluxo leve;
2. **web-admin piloto** — CRUD/admin com UI, auth, dados e E2E para validar o fluxo completo.

A V1 só deve congelar defaults que sobreviverem aos pilotos.
