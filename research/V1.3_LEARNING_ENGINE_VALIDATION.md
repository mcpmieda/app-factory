# V1.3 — Learning Engine Validation

Data: 2026-08-21

## Objetivo

Validar o item 12 da evolução pós-V1.2: aprendizado local e conservador para melhorar escolhas de executor sem ultrapassar capacidade, segurança, fallback, risco ou Definition of Done.

## Arquitetura

`engine/learning_engine.py` mantém `.factory/learning.json` como dataset local bounded. O arquivo é ignorado pelo Git e não possui telemetria externa.

Cada evento contém somente:

- timestamp;
- action class allowlisted (`other` para texto desconhecido);
- capability signature allowlisted;
- backend conhecido;
- outcome;
- duração opcional.

Prompt, código, conteúdo de arquivo, summary/log, task key, nomes e secrets não fazem parte do schema.

## Roteamento

A Execution Fabric primeiro remove candidatos:

1. indisponíveis;
2. sem capacidade obrigatória;
3. rejeitados pelo failure threshold da tarefa atual.

Somente os candidatos restantes chegam ao Learning Engine. `local_full` é protegido contra promoção estatística sobre um backend leve capaz.

## Confiança

Default:

- prior Beta(2,2);
- mínimo de 5 amostras resolvidas por backend comparado;
- margem mínima de 0,10 no posterior de sucesso;
- duração mediana só desempata quando a confiança de sucesso já é alta e próxima, exigindo redução material de duração.

Sem evidência suficiente, o modo é `insufficient-data` e a ordem V1.2 é preservada.

## Testes executáveis

`tests/v1_3/` cobre privacidade do schema, rejeição de capability desconhecida, dataset bounded, amostra mínima, aprendizado entre backends leves, incapacidade acima de score, proteção de `local_full`, failure threshold da tarefa, isolamento entre tarefas, desempate por duração, blocked/cancelled e persistência entre sessões, além da CLI.

`scripts/validate_v1_3.py` compõe esses contratos.

## CI

Workflow dedicado: `Validate V1.3 Learning Engine`.

Também permanecem obrigatórios os gates V1.2/V1.1/V1: Factory/plugin, bootstrap isolado, starter/recipes, PostgreSQL/Auth, audit project e browser E2E.

## Estado da evidência

Documento criado junto da implementação. Resultados finais do head de release serão registrados após todos os workflows concluírem com sucesso.
