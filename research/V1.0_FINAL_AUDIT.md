# App Factory V1.0 — auditoria final

Data: 2026-08-21

Branch: `audit/v1-final-release-candidate`

Baseline: `38421c037c04df1999701e56a7c8946e80bba486` (V0.9), mais o handoff documental `86de92e27d1d5d1c323e0fdd96b447e5e799689b` já presente em `main`.

## Pedido de entrada

O teste de produto começou exatamente, sem stack, arquitetura ou instrução técnica anexada:

> Quero criar um sistema simples para a escola registrar empréstimos e devoluções de equipamentos, saber quem está com cada item e identificar o que está atrasado.

Resultado do roteamento: produto `web-admin`, escala M e risco médio. Perfil `web-admin`; Next.js App Router, React, TypeScript, Tailwind/shadcn, Zod, Vitest e Playwright; recipe Drizzle + SQLite somente para auditoria local/teste; sem auth, ReUI ou nova biblioteca de motion. Motion Profile `ambient` no cabeçalho e estados espaçosos, atenuado para `subtle` na lista densa, com `prefers-reduced-motion` obrigatório. Implementação pesada roteada para Codex.

## Respostas objetivas

### 1. Factory foi inicializada em ambiente isolado sem depender da conversa/máquina antiga?

Sim. `scripts/validate_v1_bootstrap.py` cria um archive limpo do `HEAD`, um `CODEX_HOME` temporário, registra o marketplace e instala pelo Codex oficial 0.149.0. Resultado: 11 Skills descobertas, `factory-router` presente, hashes SHA-256 idênticos entre origem/cache e pacote de 5.670.616 bytes. Nenhuma configuração global foi alterada.

O binário global desta máquina era 0.133.0 e não implementava corretamente o catálogo atual; o canal npm oficial forneceu 0.149.0 e passou. A execução de uma nova inferência dentro do `CODEX_HOME` vazio exigiria login/API credential externo. Esse é o gate mínimo inevitável; instalação, descoberta, integridade, roteamento estrutural e toda a construção foram provados sem reutilizar credenciais no ambiente isolado.

### 2. O pedido simples ativou o roteamento correto sem frase especial?

Sim. O pedido acima não contém “App Factory” e ativou `factory-router`, que carregou somente planner, tool router, perfil `web-admin`, UI/motion, arquitetura, banco, segurança e verificação relevantes. Não foi criado classificador específico para a frase.

### 3. Qual tipo/perfil/stack foram escolhidos e por quê?

`web-admin`, escala M, risco médio: é uma ferramenta interna orientada a dados, com jornada administrativa, persistência e regra de integridade. O perfil já validado forneceu a menor stack comprovada. Drizzle foi ativado porque o produto possui estado; SQLite atende ao audit local de um processo, mas não é promessa de provider de produção. Auth foi dispensado porque não existe requisito de identidade e o projeto não será publicado.

### 4. O projeto final foi criado do zero usando somente reuso justificável?

Sim. `audits/v1-final/equipment-loans/` foi gerado por `scripts/create-web-admin.mjs` com o starter `web-admin` V0.7 e recipe `database-drizzle`. Não houve cópia de `asset-admin` ou pilotos. O reuso ficou limitado ao baseline, primitives shadcn e primitives de motion já promovidas.

### 5. A jornada principal funciona do começo ao fim e persiste corretamente?

Sim. O Playwright registra empréstimo, confirma responsável/data, recarrega e encontra o mesmo estado, registra devolução, recarrega novamente e encontra o item disponível. O fluxo passou em desktop e Pixel 7. A migração e o seed fictício são reproduzíveis; `npm run setup` e `npm run setup:e2e` têm alvos locais explícitos.

### 6. Segurança/regras de negócio impedem estados impossíveis relevantes?

Sim. Validação Zod, regra de domínio, transação e índice único parcial `one_active_loan_per_equipment` impedem dois empréstimos ativos. Teste integration confirma uma única linha e E2E confirma HTTP 409/`ALREADY_LOANED`. Datas passadas são rejeitadas para novos empréstimos. Devolução preserva histórico; não há exclusão destrutiva, secrets, dados reais ou conta externa.

### 7. Desktop/mobile/reduced-motion passaram?

Sim. 8 cenários Playwright passaram em Chromium desktop e Pixel 7, cobrindo jornada, regra impossível, overdue, reload, teclado, console e overflow. `agent-browser` confirmou conteúdo real, ausência de overlay e `NO_OVERFLOW` móvel. Capturas: `research/evidence/v1-final-equipment-loans-{desktop,mobile}.png`. A media query reduced motion retorna `animation-name: none` para o ambiente não essencial.

### 8. Outro agente conseguiu entender, modificar e validar o projeto sem contexto desta conversa?

Sim. Um segundo agente com `fork_turns: none` recebeu somente o caminho do projeto e a pequena missão. Recuperou produto, estado, arquitetura, comandos, limites de auth/produção e próxima mudança; detectou o filtro existente; fortaleceu o teste para `aria-current`, exclusão dos outros estados e persistência do overdue após reload; atualizou `PROJECT_STATE.md`; passou lint, typecheck, 5 Vitest e 8 Playwright. Evidência: `research/evidence/V1_CONTINUITY_HANDOFF.md`.

### 9. Uma regressão controlada foi detectada e recuperada?

Sim. Em diretório temporário fora do repositório, o preflight de overdue passou, uma alteração deliberada fez data passada retornar `loaned`, o mesmo assert falhou com actual `loaned`/expected `overdue`, a regra foi restaurada e o preflight voltou a passar. Nenhuma falha entrou na branch. Evidência: `research/evidence/V1_CONTROLLED_RECOVERY.md`.

### 10. Os gates anteriores continuam saudáveis?

Sim. Baselines GitHub anteriores estavam verdes: [Universal Pilots V0.9](https://github.com/mcpmieda/app-factory/actions/runs/32506877906), [Living UI](https://github.com/mcpmieda/app-factory/actions/runs/32502466901), [Web Admin Starter](https://github.com/mcpmieda/app-factory/actions/runs/32502466905) e [Core/Skills/plugin em main](https://github.com/mcpmieda/app-factory/actions/runs/32507049937). ### 11. Documentação/plugin/versionamento estão coerentes para release?

Sim. README contém início simples e instalação efetivamente validada; `docs/CODEX_PLUGIN.md` distingue fonte única de cache derivado; manifest usa semver `1.0.0-rc.1`; CHANGELOG contém V1 RC; PROJECT_STATE diz `V1.0 release candidate — aguardando revisão final`. Registros históricos preservam seus números de versão. Nenhuma tag/release foi criada.

### 12. Existe qualquer blocker objetivo para V1.0?

Não. O audit de dependências encontrou somente quatro advisories moderados transitivos de tooling em `drizzle-kit`; o gate high/critical passou. O `npm audit fix --force` proposto faria downgrade quebrável e não é correção segura. Deploy, provider de produção, auth e novos perfis são decisões pós-V1, não promessas desta release.

### 13. Se houver blocker, qual a menor correção necessária?

Não há blocker. A exigência restante é revisão humana do draft PR e confirmação dos checks GitHub; isso é o gate de entrega solicitado, não uma correção de produto.
