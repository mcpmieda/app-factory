# V0.5 — Web Admin Starter Validation

Date: 2026-08-21

Issue: [#10 — Gerar starter web-admin limpo e validar segundo app do zero](https://github.com/mcpmieda/app-factory/issues/10)

Branch: `pilot/web-admin-starter-v0.5`

## Result

The V0.4 `web-admin` profile now has a real starter, a safe Node generator, three conditional recipes and a second generated application for a fictitious school asset domain.

The example delivers login/logout, server-protected administration, dashboard indicators, list, search, category/status/location filters, creation, editing, location/status changes, reversible archive/reactivation, persistence and complete UI states. No real school or user data is used.

## Product A — clean starter

`starters/web-admin/template/` was created from the official `create-next-app` 16.3.2 scaffold and shadcn 4.18.0 registry, then reduced to the profile-approved base.

Included:

- Next.js App Router, React and TypeScript;
- Tailwind and shadcn/ui foundation;
- Zod, Vitest and Playwright;
- official Next ESLint configuration;
- Prettier as the small deterministic formatter required by the gate;
- continuity documents and a smoke test.

Explicitly absent from the base package:

- Better Auth and Drizzle/database providers;
- ReUI and TanStack Table;
- Biome;
- React Hook Form/TanStack Form;
- TanStack Query/Zustand;
- Sentry/OpenTelemetry/analytics;
- monorepo tooling.

The shadcn CLI dependency itself was removed after component generation; only the runtime dependencies actually imported by the approved components remain. The generated circular font token was corrected to use Geist explicitly.

## Generator and recipes

`scripts/create-web-admin.mjs`:

- accepts destination, display name and repeatable `--recipe` flags;
- recursively applies recipe requirements in deterministic order;
- refuses a non-empty destination before writing;
- removes a partial destination if generation fails;
- excludes `node_modules`, `.next`, coverage, browser artifacts, `.env`, databases and Git metadata;
- personalizes package and project metadata;
- writes `.app-factory.json` with profile, baseline, source and recipes;
- preserves npm 10.9.9 lockfile consistency.

`scripts/create-web-admin.test.mjs` proves naming, profile/baseline continuity and safe refusal to overwrite a non-empty target.

Recipes are plain metadata plus file overlays:

- `database-drizzle`: Drizzle, versioned migration, local setup and SQLite provider guidance;
- `auth-better-auth`: requires Drizzle, adds auth schema/API/client/server session checks and idempotent local admin seed;
- `advanced-ui-reui`: records a selective decision and audit procedure without bulk-installing components.

## Product B — generated asset app

The versioned app was born from:

```bash
node scripts/create-web-admin.mjs examples/asset-admin "Patrimônio Escolar" \
  --recipe database-drizzle \
  --recipe auth-better-auth
```

Its `.app-factory.json` is the provenance record. Domain code was implemented after generation, as intended for a starter.

### Conditional modules

- Better Auth was activated because login and protected mutations are requirements.
- Drizzle was activated because the app owns inventory data.
- SQLite/better-sqlite3 was selected only for local validation without an external service; it is explicitly not a production default.
- ReUI was not activated. A responsive native table/card list with server-side search and filters meets the concrete complexity with less code and no second UI layer.
- No form framework, client cache/state library, observability, analytics or monorepo layer was necessary.

### Security and data

- signup is disabled in the running app and enabled only by the controlled seed factory;
- every protected layout read and every mutation revalidates the server session;
- Zod validates input server-side;
- patrimonial code is unique in validation flow and database index;
- archive is reversible and requires explicit confirmation;
- no permanent delete action is exposed;
- `.env.local`, SQLite files, caches and test artifacts are ignored;
- setup creates a random local secret;
- migrations and seed rebuild the local state, and seed is idempotent;
- all records and identities are fictitious.

## Required answers

1. **Was the starter really generated without copying the entire pilot?** Yes. It began from official Next/shadcn scaffolds and contains none of the pilot’s auth, database, ReUI or domain code.
2. **Does the generator work in a clean tree?** Yes locally by a temporary generation test and clean generated-project verification; CI repeats this from checkout.
3. **Was the second app born from the starter?** Yes. `.app-factory.json`, generated continuity documents and the recorded command prove provenance.
4. **Did `factory-router`/profile make coherent choices?** Yes. The broad request mapped to scale M and `web-admin`; base defaults were used and optional modules were selected by requirements.
5. **Did Better Auth/Drizzle work as conditional modules?** Yes. Both are absent from the base and present together in the example, with setup, migrations, seed, auth and persistence exercised.
6. **Was ReUI used or omitted for the right reason?** Omitted. The list needs useful filters and responsive presentation, not an advanced data-grid engine.
7. **Can another agent resume from versioned artifacts?** Yes. Root/example state, product, architecture, READMEs, manifest, migrations, tests, workflow and this report carry the context.
8. **Did the process require unnecessary human intervention?** No. All routine stack, generation, recipe, migration, test and browser decisions were executed autonomously.
9. **What still blocks stable web-admin V1?** Review of this draft PR/CI, validation against a real production deployment/provider, and a maintenance policy for future Better Auth schema/version changes. The four moderate build-tool advisories should continue to be monitored; they do not breach the current high/critical gate.

## Differences from the documented profile

- Prettier was added as a formatter because Issue #10 requires a separate format gate and Biome is explicitly not default. This is a small development-only addition, not a framework substitution.
- Playwright uses one worker for the example because desktop/mobile mutate one local SQLite file; serial execution removes artificial cross-viewport contention while preserving both projects.
- The ReUI recipe remains guidance/decision automation rather than a bulk component overlay, consistent with selective registry installation.
