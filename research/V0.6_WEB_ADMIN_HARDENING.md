# V0.6 — Web Admin Hardening

Date: 2026-08-21

Issue: [#12 — Hardening pré-V1 do perfil web-admin](https://github.com/mcpmieda/app-factory/issues/12)

Branch: `pilot/web-admin-hardening-v0.6`

## Result

The V0.5 starter now tests recipes as generated products rather than inferring their health from the versioned example. A PostgreSQL provider supplies the same Drizzle capability without SQLite dependencies, composes with Better Auth through one small provider variant and is exercised against an ephemeral real PostgreSQL service in CI.

The profile is suitable for `v1-rc`: its base remains small, both local and production-style provider paths are explicit, schema drift has an executable guard and the existing SQLite application remains a regression gate. This is not a declaration that every generated project is production-ready without its own product/security/deploy review.

## Architecture

Recipe metadata gained only three small concepts:

- `provides`: one recipe may satisfy a capability required by another;
- `conflicts`: mutually exclusive providers fail before the destination is written;
- `variants`: a selected recipe may overlay only the files that differ for another selected provider.

`auth-better-auth` still requires the `database-drizzle` capability. With no explicit provider it resolves the existing SQLite recipe. With `database-drizzle-postgres`, it resolves PostgreSQL first and applies the PostgreSQL Auth schema/config variant. Explicit SQLite + PostgreSQL is rejected rather than producing an ambiguous project.

This avoids a general plugin framework and keeps the generated manifest deterministic.

## PostgreSQL provider

`database-drizzle-postgres` uses:

- `postgres` 3.4.9 and `drizzle-orm` 0.45.2;
- `DATABASE_URL` only, validated as `postgres://` or `postgresql://`;
- versioned Drizzle SQL migrations;
- a write/read persistence smoke;
- a production `next start` smoke;
- no `better-sqlite3`, SQLite types, database file or filesystem persistence.

The implementation follows the official [Drizzle PostgreSQL connection guidance](https://orm.drizzle.team/docs/get-started-postgresql) and keeps schema generation separate from applying reviewed migrations.

## Better Auth and schema maintenance

The supported recipe baseline pins `better-auth@1.7.1` and the matching `auth@1.7.1` CLI. The official Better Auth guidance requires Drizzle users to generate the ORM schema and then manage migrations through Drizzle; the recipe encodes that separation in `auth:schema:check` and the short maintenance policy. See the official [Better Auth database guide](https://better-auth.com/docs/concepts/database) and [Drizzle adapter guide](https://better-auth.com/docs/adapters/drizzle).

The executable check asks the pinned CLI to generate its schema in a temporary directory and compares provider, tables, fields and indexes with the committed schema contract. An upgrade must move both pins, review the generated diff and add a migration. Applied migration history is never rewritten, and destructive SQL requires explicit recovery/backfill analysis.

The PostgreSQL/Auth smoke creates an idempotent fictitious admin, signs in through the real Better Auth HTTP handler, forwards its session cookie and verifies that `get-session` recovers the same identity from PostgreSQL.

Local Windows did not provide Docker/PostgreSQL. No database result is inferred from the static local build: the GitHub Actions service container is the authoritative real-PostgreSQL evidence.

Four moderate transitive esbuild advisories remain in the Drizzle/tsx development toolchain. The high/critical audit gate passes; the proposed automatic fix is a breaking Drizzle Kit downgrade and was not forced.

## Required answers

1. **Are recipes now tested directly in clean generation?** Yes. CI generates database-only, Auth-only, explicit SQLite/Auth and PostgreSQL/Auth projects independently from the versioned example.
2. **Does Auth alone resolve its database dependency correctly?** Yes. It resolves `database-drizzle` first and records `[database-drizzle, auth-better-auth]` exactly once.
3. **Does PostgreSQL work as a production provider without contaminating the base?** Yes. The base package remains unchanged; PostgreSQL is selected only by recipe and uses environment configuration without local persistence.
4. **Do Better Auth and PostgreSQL work together in real CI?** Yes. The service-container gate runs migrations, seed, login and session recovery against PostgreSQL.
5. **Are SQLite provider dependencies left in the PostgreSQL project?** No. Generation and CI explicitly reject `better-sqlite3` and `@types/better-sqlite3`; `postgres` is required instead.
6. **Is the schema maintenance contract clear and proportional?** Yes. One short policy and one generated-contract command cover pinning, detection, migration review, destructive-change safety and existing-project compatibility.
7. **Is the project deploy-ready without local filesystem persistence?** Yes. Production build and `next start` smoke use only injected variables and PostgreSQL. Deployment-specific scaling, TLS and pool limits remain the generated project's responsibility.
8. **Is there a real human gate for public deployment?** Yes, and only at that boundary: authorization to choose/create a hosted PostgreSQL/deployment account, provision resources, inject secrets and expose a public URL. No credential or paid resource was invented.
9. **Can `web-admin` be promoted to `v1-rc`?** Yes, once this draft's required checks are green. Stable V1 should still include review of this PR and at least one authorized public deployment/operational exercise; that is a release-confidence gate, not a blocker to the reusable recipe architecture.

## Rollback and compatibility

The V0.5 SQLite recipe and versioned app are preserved. Rolling back this change removes the new recipe metadata/provider/workflow without migrating any real data because all PostgreSQL verification uses an ephemeral CI database. Existing generated applications are not automatically upgraded by changes to the Factory baseline.

## Handoff

Review the draft PR and the full `Validate Web Admin Starter` matrix. Do not merge automatically. A public deploy should be a separate authorized task because it requires an external account/resource and real secret management.
